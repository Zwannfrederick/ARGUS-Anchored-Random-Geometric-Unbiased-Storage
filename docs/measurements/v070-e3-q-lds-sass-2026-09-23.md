# v0.7 E3 candidate: Q shared-load vectorization — REJECTED at the compiler gate

The proposed experiment was a `cells-kq` path whose only causal change is vectorizing
and coalescing the query reads out of `query_tile`. The gate placed before any
benchmark was: prove in SASS that the Q loads become a wider, fewer LDS form.

**They are already that form.** nvcc emits the theoretical minimum today, so the
transformation has no before state to improve and the experiment is rejected without
being implemented. Raw data: [`v070-e3-2026-09-23/`](v070-e3-2026-09-23/)
(`cells-kc-sm86.sass`, `cells-kc-shared-ops.txt`).

Built with the build's own command line plus `-arch=sm_86 -lineinfo -cubin`, from
`b0255fe`, disassembled with `cuobjdump -sass` and `nvdisasm -c -g`.

## 1–2. Q loads: number, width, contiguity, alignment

Source lines 318–319 (`qs[i]`, `qs[i+16]`, `qs[i+32]`, `qs[i+48]`) compile to exactly
**16 `LDS.128` per tile**, all inside the tile loop:

```
/*11b0*/ LDS.128 R24, [R55]        /*11c0*/ LDS.128 R32, [R55+0x80]
/*1300*/ LDS.128 R40, [R55+0xc0]   /*1310*/ LDS.128 R28, [R55+0x40]
/*1600*/ LDS.128 R40, [R55+0x10]   /*1620*/ LDS.128 R44, [R55+0x90]
/*1720*/ LDS.128 R8,  [R55+0x50]   /*1800*/ LDS.128 R16, [R55+0xd0]   <- pass 0
/*19d0*/ LDS.128 R24, [R55+0x20]   /*19e0*/ LDS.128 R20, [R55+0xa0]
/*19f0*/ LDS.128 R16, [R55+0x60]   /*1a80*/ LDS.128 R24, [R55+0xe0]
/*1b50*/ LDS.128 R20, [R55+0x30]   /*1c00*/ LDS.128 R16, [R55+0xb0]
/*1cf0*/ LDS.128 R24, [R55+0x70]   /*1d00*/ LDS.128 R36, [R55+0xf0]   <- pass 1
```

The offsets are `0x00, 0x10, … 0xf0`: sixteen consecutive 16-byte chunks covering the
whole 256-byte query row (`__shared__ float query_tile[4][64]`, 256 B per warp, so the
base is naturally 16-byte aligned). Pass 0 takes `qs[0..7, 16..23, 32..39, 48..55]`,
pass 1 the complement; **every one of the 64 floats is loaded exactly once per tile**.
16 x 16 B = 256 B is the data the tile provably needs, and `LDS.128` is the widest
shared load in the sm_86 ISA. There is no redundancy to remove and no width to add.

## 3. Sub-128-bit shared accesses anywhere in the kernel

Every `LDS` in `cells-kc` is `.128` — 28 of them statically, zero scalar or 64-bit
loads. The only narrow shared operations are stores:

| source | op | per tile | note |
|---|---|---|---|
| 268–269 | `STS` x2 (32-bit) | — | fills `query_tile`, once per **row**, amortized over ~126 tiles |
| 289, 291, 292 | `STS.64` x3 (predicated) | 1 taken | `value_rows[warp][lane]`, and the masked-lane null publication |
| 385 | `STS.64` | 1 | `weights[warp][lane]` |

Widening the two `STS.64` by interleaving each cell's weight and row pointer into one
16-byte record converts 2 x `STS.64` (32 lanes x 8 B = 2 wavefronts each) into
1 x `STS.128` (4 wavefronts) — identical wavefront work, one fewer instruction — and
leaves the read side unchanged, because the V loop already reads 4 `LDS.128` per
unrolled group of 4 cells either way. It is also not a Q change.

## 4. Bank behaviour

The Q addresses do not depend on `lane` (`i` is a compile-time constant of the unrolled
`e` loop), so all 32 lanes read the same address: a broadcast, structurally
conflict-free. E1's measured 0.37 M shared bank conflicts (1.7% of shared wavefronts)
come from the K tile's lane-distinct swizzled access at lines 302/307, not from Q.

## 5. How much of the 12.0 M is Q

Per-tile shared instruction census from the SASS, with the V-loop body counted at its
8 trips (32 cells, `#pragma unroll 4`):

| source | op | per tile | lane pattern |
|---|---|---:|---|
| 318–319 | `LDS.128` **Q** | **16** | warp-uniform broadcast |
| 393 | `LDS.128` weights | 16 | warp-uniform broadcast |
| 394 | `LDS.128` row pointers | 16 | warp-uniform broadcast |
| 302 | `STS.128` K tile | 8 | lane-distinct, swizzled |
| 307 | `LDS.128` K tile | 8 | lane-distinct, swizzled |
| 289/291/292/385 | `STS.64` | 4 | lane-distinct |

Q is 16 of the 48 warp-uniform `LDS.128`, so of E1's 12.0 M "q/weight/pointer" shared
wavefronts roughly **one third, ≈4.0 M**, is Q — about 19% of the kernel's 21.4 M
shared wavefronts and **≈11% of its 35.9 M L1TEX data-pipe wavefronts**. The weight
and row-pointer broadcasts in the V loop are together exactly twice Q's traffic.

## 6. Arithmetic invariance

Moot: there is no transformation to check.

## Why nothing else about Q is in scope

Q's shared traffic can only fall by reading the row fewer times, and both ways out are
excluded by this experiment's own single-factor rule and by arithmetic:

- **Register caching** needs 64 floats resident per thread against a 66-register
  budget. It is not a tuning question, it does not fit.
- **Consuming more cells per Q read** (two tiles per iteration) is a loop restructure
  and raises register pressure.

## Sensitivity, for the record

E1's transfer function was −23% data-pipe wavefronts → −12% kernel → −6.7% prefill,
about 0.29% of prefill per 1% of wavefronts. Even a hypothetical *complete* removal of
Q's shared traffic (−11% of data-pipe wavefronts) maps to ≈−3% prefill, the bottom of
the acceptance band — and it is not on offer. The transformation actually proposed,
vectorization, is worth exactly zero: Q `LDS` instruction count before 16, after 16.

## Verdict

REJECT before implementation. No `cells-kq` path is written, and per the instruction
no replacement experiment is selected in this turn. `cells-kc` remains the default and
`b0255fe` remains the accepted checkpoint.
