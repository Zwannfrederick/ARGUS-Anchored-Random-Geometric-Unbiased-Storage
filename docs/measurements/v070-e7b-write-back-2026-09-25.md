# v0.7 E7b: GPU appends with background disk write-back — ACCEPT

The second half of the user's decision on audit L2.1: GPU-written KV in the disk-backed modes too, with the disk copy published in the background. Raw data: [`v070-e7-2026-09-25/e7b/`](v070-e7-2026-09-25/e7b/).

## Change

**Scope.** Every policy-on store with a GPU tier, F16 KV and page-aligned rows. GPU-control stores keep E7a's behaviour. **Policy off** is excluded on purpose: it is the reference disk path, and a GPU append would make placement decisions that mode must not make.

**Append (`argus_disk_gpu_rows`).** Every touched page gets a GPU copy:
- a page already on the GPU is used in place;
- a written page that lives elsewhere, or only on disk, is uploaded — a promotion by write;
- an unwritten page starts zeroed.

The encode kernel runs and finishes under the store lock, so no reader or flusher ever sees a half-written page. The new revisions are then published with a pending digest, and the pages are marked **dirty**.

**Host fallback.** The op copies the rows to the host and takes the unchanged host append (`argus_disk_append_rows`, factored out of the CPU op) when the GPU budget cannot hold all three of:
- the new pages,
- the row table,
- the attention scratch headroom the policy keeps free.

**Flusher.** One worker per store; its stack is charged to staging. For each dirty page it:
1. takes a snapshot under the store lock: the bytes, the digest, the content revision and the published slot;
2. writes and verifies the inactive slot while holding only the new `io_mutex`;
3. publishes the slot and clears the page's dirty flag, only if neither the content revision nor the published slot changed in the meantime. Otherwise the page stays queued.

Locking rules:
- `active` changes only with both locks held, always taken store → io. The flusher never holds io while waiting for the store lock.
- `write_page` and the synchronous flush take the io lock for their slot I/O.

**Readers and policy.**
- Readers already prefer the resident copy.
- Demoting a dirty page flushes it synchronously first.
- `clear(0)` drops the dirty queue with the content.
- Teardown joins the worker before the pages go.
- `argus_disk_flush(tensor)` publishes everything now, and clears a background error once it has recovered from it.

**Durability contract (user decision).** After a crash, the disk copy can trail the GPU by the dirty pages. In the measured 4K request, 15.3 of 52.3 MB had been published by the end of the request; the rest followed in the background. Every published slot is still verified, and the previously published slot is kept until the new one verifies.

## Design mistakes the measurements caught

1. **Flusher I/O under the store lock.** The first version wrote and verified each page's slot while holding the store lock. Attention holds the same lock while its kernel runs, so the two serialized. Profile: attention 1.53 → 5.94 s, and policy-on did not improve at all (8.0–8.5 s either way; `policy-on-locked-flusher/`, `prof-e7b.json`). Fixed by giving slot I/O its own lock.
2. **Appends filling the scratch headroom.** At the tight budget (GPU 2 MiB), appends filled the tier, and each attention call's `prepare()` then force-demoted dirty pages. Demotions rose from 34 to 12,314, and prefill regressed to 52–55 s (`tight-budget-before-headroom/`). This is the write-side twin of E6's L0.3. Fixed by counting the policy's headroom (`argus_kv_policy_headroom`) and the row table in the append's budget check.

## Tests (TDD, mutation-checked)

- `check_gpu_write_back`:
  - an append on a policy store is byte-exact;
  - written pages become GPU-resident, and the untouched page stays unwritten;
  - after `argus_disk_flush`, demoting every page and reading back returns the new bytes;
  - demoting without an explicit flush preserves the new bytes;
  - a short write during a flush throws, and the GPU copy stays intact and authoritative; the retry succeeds;
  - a tiny budget falls back to the host append;
  - room for the pages but not for the headroom also falls back.
- Mutations: removing the flush before demotion fails the test; a flush that does nothing fails the test.
- Native suite: 15 passed, 2 skipped. Python suite: 382 passed, 6 skipped. Hash `a152ed56` on every benchmark run.

## Results (4K, Qwen2.5-0.5B Q4_K_M, F16 KV, ubatch 64; one `llama-server`, `libllama.so` switched with `LD_LIBRARY_PATH`; E7a = `42cee14`)

| mode | E7a prefill | **E7b prefill** | E7a decode | **E7b decode** |
|---|---:|---:|---:|---:|
| policy-on, 64 MiB GPU (3 + 2 alternating pairs) | 7.97–13.59 s | **1.96–2.16 s** | 16.4–20.0 tok/s | **36.7–41.2 tok/s** |
| policy-on, 2 MiB GPU (2 pairs, final code) | 45.8 / 46.0 s | 45.9 / 46.7 s | 1.05 / 1.07 | 1.08 / 1.02 |
| GPU control (3 pairs; path unchanged) | 1.94 s median | 1.96 s median | 43.9 | 43.6 |

- **Policy-on 4K is about 4x faster on prefill, and decode more than doubles.** The product mode is now within a few percent of GPU control and faster than stock on decode (stock ≈ 38 tok/s).
- The tight budget is unchanged. Its counters match E7a exactly, because the tier has no room beside its headroom, so every append takes the host path.
- The E7a policy-on arm varied a lot (8.0–13.6 s) because of disk contention from other processes during this session. E7b no longer waits on the disk in the request path.
