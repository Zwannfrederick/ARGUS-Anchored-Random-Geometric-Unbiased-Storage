# v0.7 E2: the GPU-control page-write path (4K) — ACCEPT

Two factors, measured one at a time in the same binary, both on the CPU-side critical
path that [nsys](../../plans/argus-v0.7.0.md#macro-timeline-nsight-systems-2026-09-18)
attributed the +0.58 s of extra GPU idle to. Neither changes any arithmetic, any
placement decision or the verification contract; the attention kernel is untouched.
Raw data: [`v070-e2-2026-09-23/`](v070-e2-2026-09-23/).

## Why this path and not more attention work

E1 left attention at ≈1.16 s of kernel events and the CPU page-write path second.
`write_page` under GPU control costs, per page: two FNV-1a digests over 4096 bytes, a
`cudaMalloc`, a blocking 4 KiB H2D, a blocking 4 KiB D2H read-back and a `cudaFree`.
Measured directly on this GPU before touching anything (12,000 pages, the prefill's
count; [`pagecost.cu`](v070-e2-2026-09-23/pagecost.cu),
[`batchcost.cu`](v070-e2-2026-09-23/batchcost.cu)):

| per-page cost | measured | per prefill |
|---|---:|---:|
| FNV-1a over one page | 5.34 us | 64 ms x2 |
| hardware CRC32C over one page | 0.44 us | 5 ms x2 |
| blocking 4 KiB H2D, pageable | 7.37 us | 88 ms |
| blocking 4 KiB D2H, pageable | 8.76 us | 105 ms |
| `cudaMalloc` + `cudaFree`, 4 KiB | 3.34 us | 40 ms |

Pinning the host side alone does **not** help at this size (4 KiB H2D 8.17 us pinned vs
7.37 us pageable, D2H 7.83 vs 8.76): the cost is the blocking API round trip, not the
staging copy. Four pages per flush, queued on one stream with a single wait, is what
moves it: 18.8 us per page falls to 8.7 us. That measurement chose both changes below.

## E2a — hardware CRC32C page digest

`checksum()` uses `crc32q` over eight bytes at a time when the CPU reports SSE4.2,
and keeps FNV-1a as the fallback and as a same-binary reference
(`ARGUS_KV_CHECKSUM=fnv`, `--checksum` in the bench). Digests live in memory only —
`Page::checksum`, never a file header — so the choice has to be stable within a
process, not across builds. Both remain corruption detectors, not authenticity checks.

7 alternating pairs, 4K GPU-control, profiler off:

| | fnv | crc32c | change |
|---|---:|---:|---:|
| prefill median (min–max) | 2.672 s (2.638–2.878) | **2.557 s** (2.539–2.639) | **−4.3%**, crc32c faster in 7/7 |

## E2b — whole-page runs committed together

`set_rows` staged one page at a time, so a 64-row ubatch reached the store as four
single-page writes. It now stages the whole call (capped at 64 KiB *and* at the free
staging budget, so a tight budget keeps exactly the old behaviour), and `transfer()`
hands the resulting run of whole pages to `write_run`.

`write_run` keeps `write_page`'s contract per page — a separately budgeted destination
is written, read back and compared before the old page is released — and shares only
the copies: the run's uploads and read-backs are queued on one private stream from
store-owned pinned staging and waited for once. Publication is now all-or-nothing for
the run, which is stricter than before, where an earlier page of a flush could already
be published when a later one failed. `ARGUS_KV_PAGE_COMMIT=page` keeps the per-page
commit selectable (`--page-commit`).

7 alternating pairs, CRC32C in both arms:

| | page | run | change |
|---|---:|---:|---:|
| prefill median (min–max) | 2.529 s (2.427–2.679) | **2.387 s** (2.286–2.624) | **−5.6%**, run faster in 6/7 |

| scope | page/fnv | page/crc32c | run/fnv | run/crc32c | calls (page → run) |
|---|---:|---:|---:|---:|---|
| `set_rows` | 0.566 | 0.434 | 0.412 | **0.309** | 3072 |
| `write_page` | 0.461 | 0.331 | 0.325 | **0.214** | 12096 → 3072 |
| `tier_read` (D2H verify) | 0.204 | 0.196 | 0.086 | **0.089** | 12096 → 3072 |
| `tier_write` (H2D) | 0.052 | 0.049 | 0.038 | **0.038** | 12096 → 3072 |
| `checksum` | 0.136 | 0.015 | 0.132 | **0.015** | 24192 |
| `allocation` | 0.052 | 0.052 | 0.052 | 0.054 | 13632 |
| `release` | 0.027 | 0.026 | 0.029 | 0.030 | 7560 |
| `synchronization` | 1.154 | 1.162 | 1.166 | 1.173 | 1536 |

Each change moves exactly its own scope and nothing else: the digest change is visible
only in `checksum`, the run change only in the copy scopes and their call counts.
Attention and synchronization are flat across all four cells, which is the control.
`write_page` now counts flushes, not pages.

**Costs paid.** Pinned staging of `2 x run_pages x 4096` per store, released with the
store: `peak_pinned_bytes` 32,768 → 65,536 against a 64 MiB budget. `peak_staging_bytes`
(73,728) and `peak_gpu_bytes` (49,582,080) are unchanged.

## Final baseline (profiler off, 5 repeats, idle GPU)

[JSON](v070-e2-2026-09-23/e2-final-baseline.json)

| mode | prefill median (min–max) | vs stock | decode |
|---|---:|---:|---:|
| stock-host | 1.342 s (1.340–1.389) | 1.00x | 37.02 tok/s |
| GPU-control | **2.406 s** (2.370–2.424) | **1.79x** | 8.08 tok/s |

Against E1's 2.709 s (2.687–5.917): **−11.2%**. M1 (< 2.70 s) and M2 (< 2.50 s) are
met; M3 (< 2.25 s) is not. Decode rises 7.08 → 8.08 tok/s, from the digest change on
the single-row decode writes.

Policy-on regression check, 3 repeats: 9.142 / 9.178 / **9.349** s, median 9.178 s
against E1's 10.04–10.43 s. That path is dominated by disk noise; it is recorded as
no regression, not as a win.

**The E1 outlier was not reproduced.** 43 GPU-control prefills ran today across the
two A/Bs, the baselines and the profiled runs; the slowest was 2.878 s. E1 saw 5.917 s
in one of five and 5.27 s in an earlier attempt. 24k blocking driver round trips per
prefill is a credible source and they are gone, but this is an absence of the symptom
over 43 runs, not an attributed fix.

## Verdict: ACCEPT (both)

E2a is 4.3% on its own, below the 5% bar, and E2b is 5.6%. They are accepted together
as one write-path campaign at −11.2%, with each factor's mechanism isolated in the
profiled grid above.

**Remaining bottleneck.** Attention is now overwhelmingly dominant: 1.256 s inclusive,
1.160 s of it waiting for the kernel, against 0.309 s for the whole of `set_rows`. What
is left of the write path is the per-page allocator — `allocation` 0.053 s plus
`release` 0.030 s, still 12,048 `cudaMalloc`/`cudaFree` pairs of 4096 bytes. One 4 MiB
slab per 1024 pages measured 0.5 ms against 20.3 ms for the same pages allocated
singly, so a slab would recover ≈0.07 s, but it makes a page's device memory shared
with its neighbours' and can hold a whole slab for one live page. That trade is worth
its own experiment, and it is now smaller than anything in the kernel.
