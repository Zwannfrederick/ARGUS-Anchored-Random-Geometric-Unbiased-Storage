# v0.6: 4K resident attention datapath

The `89eaf06` attribution baseline and its reports are unchanged. Placement policy
code is unchanged. No 262K benchmark was run. This measures Qwen2.5-0.5B-Instruct
Q4_K_M weights with F16 KV on RTX 3050 Ti Laptop (4 GiB), i5-11300H and the same
SATA-backed KV directory used in the attribution report.

## Fixed workload and evidence

All runs use context 4096, exactly 4016 input tokens, 16 generated tokens
(15 decode evaluations), ubatch 64, six CPU threads, one full-workload warmup per
fresh server, 64 MiB GPU / 64 MiB pinned / 4 MiB staging / 4 MiB resident budgets.
Retained context is 4031 tokens, with no truncation or prompt-cache reuse.
Input SHA256: `b26302d3f09b7516317d9c9bfd1ddac17a667b123199a803a29bd3f6526282b4`.
Each JSON contains model, server, libllama and harness hashes; new artifacts also
record relevant source hashes. Timings are server prompt/decode timings, not TTFT.

- [Fresh original baseline](v060-datapath-before-2026-09-18.json): original binary,
  CUDA profiling enabled, one measured repeat.
- [Direct resident scalar](v060-datapath-direct-2026-09-18.json): commit `6f1ef8c`,
  same workload/profiling, one measured repeat, before batching.
- [Batched resident](v060-datapath-batched-2026-09-18.json): same workload/profiling,

- [Stock/control/policy-on](v060-datapath-comparison-2026-09-18.json): final binary,

## Design and correctness

The resident path borrows GPU page pointers while holding the registry and both
K/V store locks. It requires Q>1, F16, aligned half values, compatible packed
strides and every written page GPU-resident. Cleared/unwritten pages read as zero.
The bounded pointer table is charged to staging and GPU budgets. A completion
wait protects the pointers, pages and table until the callback returns, including
exception cleanup. Writes, migration and teardown cannot free a borrowed page.
The registry lock serializes concurrent requests: this is a known throughput
ceiling, not a claim of scalable concurrent serving.

The first stage bypasses the 32-cell payload staging but keeps the scalar kernel.
The second stage assigns one query/head to a warp, four warps to a block, and
processes the entire context in a single kernel per attention invocation. Query
values and softmax accumulators remain in registers. The original 256-lane FP32
reduction tree is reproduced exactly; explicit multiply/add/FMA operations
preserve its order. A D=256 test caught NVCC contracting the other multiplication
in the final unrolled accumulator; explicitly matching the staged FMA fixed the
failure. No tolerance was widened.

`ARGUS_KV_ATTENTION_PATH=staged|direct|batched` (or benchmark `--attention-path`)
retains both reference paths; default is batched. Q=1 decode, nonresident KV and
insufficient resident-path scratch capacity retain staged attention. Policy
prepare/observe and 32-cell successful-read history are preserved. No policy
algorithm or budget limit was changed.

Passed: five native GPU tests and five CPU/context tests. Coverage includes
D=48/64/256, exact staged/direct/batched float-vector equality, F16/F32 masks,
nonzero bias, fully masked queries, shifted views crossing pages, GQA and partial
warp-block tails, distinct K/V stores, Dk != Dv, zero/unwritten pages, concurrent
write exclusion, callback failure, decode fallback, lifecycle, migration,
policy off/on, strict logits and unchanged budget/rollback gates. The existing
double-reference attention error bound remains 1e-4.

All ARGUS measured completions retain SHA256
`a152ed5676e2f9f4412d7aadffa7054cc438c021549ecb4f472a83c864acba0a`.
Stock answers the same needle correctly but has a different continuation, as at
the attribution baseline; this is not a claim of full stock-output parity.

## Synchronization dependencies

The original staged path had K/V transfer waits, per-slot reuse waits, final
compute completion, a duplicate compute-drain teardown wait and transfer-stream
teardown wait. Stage 1 disarms the cleanup drain after successful final completion.
Stage 2 removes the transfer teardown wait: `argus_disk_stage_cuda` already drains
each K/V transfer, including errors, before releasing source pages. Staged decode
therefore removes two redundant waits per attention invocation (720 total).

Required waits remain: copies finish before source locks release and kernels
consume the tile; each double-buffer slot waits for its previous kernel before
reuse; compute finishes before buffers are freed. Resident prefill has one final
completion wait per invocation, 1512 total. The batched kernel replaces the
scalar block-wide barriers per cell with warp-local operations. Further async
lifetime changes were not bundled into this optimization.

## Reproduction

```sh
.venv/bin/python benchmarks/bench_llama_paged_context.py \
  --server "$PWD/scratch/llama.cpp-v050/build-cuda/bin/llama-server" \
  --model "$PWD/scratch/models/qwen2.5-0.5b-instruct-q4_k_m.gguf" \
  --kv-dir "$PWD/scratch/kv" --contexts 4096 \
  --modes argus-cuda-control --kv-type f16 --resident-bytes 4194304 \
  --gpu-bytes 67108864 --pinned-bytes 67108864 --staging-bytes 4194304 \
  --ubatch 64 --predict 16 --warmups 1 --repeats 1 --profile \
  --attention-path batched --request-timeout 600 --output /tmp/batched.json
```

Use `direct` and `staged` for same-binary A/B. For the final comparison omit
`--profile`, set `--repeats 3` and use modes
`stock-host-kv argus-cuda-control argus-cuda-on`. Run serially on an idle GPU.

Native verification commands (CUDA build and stories15M test model):

```sh
export ARGUS_LLAMA_CPP_DIR="$PWD/scratch/llama.cpp-v050"
export ARGUS_LLAMA_BUILD=build-cuda
export ARGUS_TEST_GGUF="$PWD/scratch/models/stories15M.gguf"

  -k 'cuda_tier_migration or cuda_gpu_control or cuda_attention_native_lifecycle or cuda_policy'
.venv/bin/python -m pytest -q tests/test_context_ladder.py tests/test_native_llama_paged.py \
  -k 'context_ladder or direct_disk_pages or paged_kernel or paged_workers'
```
