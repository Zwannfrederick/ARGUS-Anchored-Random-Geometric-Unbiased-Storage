# v0.6: Nsight Compute attribution of the lane-per-cell kernel (`78812c1`)

No source change and no commit in this step. Nsight Compute 2026.3.1 ran as root
(driver `RmProfilingAdminOnly=1`) with its defaults: base clock lock (≈1.48 GHz) and
cache flush before every replay pass. **Durations here are profiler-only**. They are
used for ratios between captures and are never compared with the profiler-off
benchmark medians. The library has no `-lineinfo`, so attribution is at SASS/PC level.
Region labels come from the kernel's SASS structure.

Artifacts: [`v060-ncu-cells-2026-09-18/`](v060-ncu-cells-2026-09-18/). It holds the
three `.ncu-repz` files, the harness JSONs and `summary-metrics.json`.

Across the whole kernel: long_scoreboard 69.1%, wait 9.0%, short_scoreboard 7.7%,
selected 5.9%, not_selected 3.7%, math_pipe_throttle 1.8%, mio_throttle 1.8%.

Top long-scoreboard PCs are the four unrolled copies of the value load consumer:
`0x26a0`, `0x2420`, `0x2560` and `0x22e0` (`@P0 HADD2.F32 R16, -RZ, R10.H0_H0`). They
hold 20.3%, 19.2%, 18.7% and 17.9% of all long-scoreboard samples, 76% combined; with
the second element of each row it is ~81%. The K-row conversions in the score region
(`0x0ca0`, `0x0d60`, `0x0e20`) hold another ~16%.

Per cell, the sequential loop compiles to one basic block guarded by the mask-bit
branch (`@!P BRA`), so nothing crosses cells:

```
LDS.64 R12,[vrow]      ; V row pointer (written in the parallel phase)
ISETP R12 != 0         ; short_scoreboard waits on the LDS
LEA/IADD3.X            ; addresses of v[lane], v[lane+32]
LDG.E.U16.CONSTANT ×2  ; V load
FFMA sum               ; independent, issues
HADD2.F32 ×2           ; <-- waits for the V load (long_scoreboard)
FMUL, FFMA acc ×2
@!P BRA next cell
```

Early context shows the same shape: V consumer 44.4%, score 24.6%, sum 0.1%, acc 1.6%.

## Answers

1. **Dominant stall (measured).** Long scoreboard: 69% of samples, 12.0 of 18.1
   cycles between issues per warp.
2. **Where (measured).** 57% of all samples sit on the `HADD2.F32` that consumes the
   sequential loop's V `LDG.E.U16`; about 11% sit on the K-row conversions in the
   score phase.
3. **Are V global loads on the critical path? Yes (measured).** Each cell runs
   `LDS` (pointer) → `LDG` (V) → use serially, and the per-cell branch keeps the
   next cell's load from issuing early. Memory-level parallelism for V is one cell
   per warp.
4. **Is 58 registers / 1.40 waves the bottleneck? Secondary (measured +
   inferred).** Achieved occupancy is 50% against 66.7% theoretical (the partial
   wave of 64 blocks). More warps would hide some latency, at most ~1.35x
   (5.9 → 8 warps per scheduler). The only way seen so far to get there
   (`__launch_bounds__`) spilled and lost.
5. **Eligible and issued warps (measured).** 0.60 eligible and 0.33 issued per
   scheduler per cycle. Two thirds of issue slots are empty because warps wait on
   memory, not because issue is saturated (not_selected 0.84 cycles). The kernel is
   latency bound.
6. **Early → late (measured).** L1 94.0 vs 93.4%, L2 93.3 vs 93.4%, DRAM
   proportional to the working set; long_scoreboard per issue rises from 10.0 to
   12.0 cycles. Duration per unmasked cell is only ~6% higher late. There is no
   L2 working-set cliff at 4K.
7. **Classification (measured).** Latency bound on a serialized L1-hit load chain.
   Not bandwidth bound (L2 3%, DRAM ≈1 GB/s, L1 45%) and not issue bound (33%).
8. **Old D64 → cells (measured).** The old kernel was mostly issue bound: 75% issue,
   2.69 eligible, not_selected 2.6 and math-pipe 1.0 cycles per issue, 468 M warp
   instructions. Cells removed 71% of those instructions and the issue pressure;
   what dominates now is the exposed latency of the dependent V-load chain,
   which the old kernel had partly hidden behind its 1.7x more resident warps
   and its instruction stream.
9. **Why only ~1.6x (measured).** Time is roughly `max(issue, latency)`. Instructions
   fell 3.46x, but issued-per-cycle fell 2.3x (0.75 → 0.33), because each warp now
   waits ~12 cycles per instruction on memory and has fewer co-resident warps
   (5.9 vs 9.9 per scheduler). The ratio of the two, 3.46 / 2.3 ≈ 1.5x, matches the
   1.60x duration ratio in these captures.
10. **Is the exact cell-order FFMA chain critical? No (measured).** `sum` FFMA 0.2% and
    `acc` FMUL/FFMA 1.7% of samples; their stalls are `wait` (fixed latency), never
    long_scoreboard. The bit-exact ordering is not what limits the kernel.

## Hypotheses

| Hypothesis | Verdict |
|---|---|
| H1: V global-load latency / dependent memory chain | **confirmed**, dominant (57% of samples) |
| H2: 58 registers / 1.40 waves | real but secondary (achieved 50% vs 66.7% theoretical); not the first lever |
| H3: L1/L2/DRAM bandwidth or cache pressure | **refuted**: hit rates 93–94%, L2 3%, DRAM ~1 GB/s, no early→late cliff |
| H4: exact FFMA accumulation chain | **refuted**: ≤2% of samples, no memory stalls |
| H5: shared-memory / shuffle / sync | minor: 0 bank conflicts, mio_throttle 1.8%, short_scoreboard 7.7% (mostly LDS→pointer use) |
| H6: branch/control flow | not as branch stalls (branch_resolving 0.2%). Indirectly yes: the per-cell branch serializes the V chains, and mask/address/branch code is 34% of instructions |
| H7: attention-outside wall-clock | not measured by ncu; earlier CUDA-event profiles put GPU-control prefill minus kernel at ~1.8 s. nsys not needed to choose the next kernel step |
| Earlier "cells is no longer issue bound" (estimate ~27%) | **confirmed** (33%) |
| Earlier "old kernel issue bound" (estimate 64–68%) | **confirmed** (75%) |

## Floors (estimates, labelled)

- **Attention kernel.** If the V chain latency were hidden and issue reached the old
  kernel's 0.75/cycle with today's instruction mix, the late capture would take about
  3.64 × 0.33/0.75 ≈ 1.6 ms instead of 3.64 ms. Applied to the 2.20 s profiled kernel
  total, that suggests an exact-order floor of roughly **1.0 s** without changing
  instruction count. This is an estimate, not a measurement.
- **Outside attention.** ~1.8 s of GPU-control prefill (profiled, CUDA events). A
  perfect kernel would leave GPU-control around 2 s, about 1.5x stock-host.

## Next experiment (one)

**Give the sequential loop memory-level parallelism for V without changing
arithmetic: make the per-cell step branchless (predicated), so the loads of the
unrolled cells can be in flight together.**

- **Evidence.** 57% of samples wait on the V consumer, one cell's load in flight per
  warp, the per-cell `@!P BRA` block boundaries, 0.60 eligible warps, bandwidth unused.
- **Causal factor.** Load-level parallelism of V inside a 32-cell tile. Nothing else.
- **Minimal implementation.**
  - In the parallel phase, write a null V-row pointer for masked lanes.
  - In the sequential loop, replace `continue` with a predicate: select
    `sum`/`acc` to their old values for masked cells, a pure select with no
    arithmetic on masked cells.
  - Keep `#pragma unroll 4` (or 8) so NVCC can issue the loads of several cells
    before the first `HADD2`.
  - Check the SASS before measuring: loads of ≥2 cells should precede the first
    consumer.
- **Correctness category 1 (exact order preserved).** The same `__fmaf_rn`/`__fmul_rn`
  sequence runs in the same cell order for live cells. Masked cells perform no
  arithmetic on `sum`/`acc` (select, not `fma(1, acc, 0)`, which could turn −0 into
  +0 or propagate NaN from 0·v). The existing exact-parity suite, the Qwen scattered-mask
  and zero/tie cases and the mutation checks apply unchanged.
- **Expected counter signature.** The `HADD2` V-consumer share falls well below
  57%. long_scoreboard per issue drops from 12 toward the K-load level, eligible
  warps rise above 0.6 and issued per cycle rises from 0.33. Registers may grow by a
  few; they must stay ≤ 64 (8 blocks/SM) with no spill.
- **Expected wall clock (estimate).** Kernel 2.2 s → ~1.4–1.7 s profiled; GPU-control
  prefill ~3.7 s → ~3.0–3.3 s.
- **Acceptance.** Bit-exact parity everywhere, and GPU-control prefill median improves
  ≥ 8% with non-overlapping 3-repeat ranges. Confirm with one ncu capture of the same
  late launch showing the signature above.
- **Rollback.**
  - Registers > 64 or any spill.
  - SASS still shows one cell's load per block.
  - Gain < 5%, or parity failure.

  A negative result is documented, not kept.

## Deprioritized by these counters

- **Shared-memory GQA reuse.** L1 already hits 94% and DRAM/L2 are idle; the 7x
  head reuse is being captured by cache. It would add barriers and shared memory for
  a bandwidth problem that does not exist.
- **Shared-memory V tile / cp.async double buffering.** Could fix the same latency,
  but costs 4 KiB+ per warp and occupancy. Try only if the branchless loop cannot
  get two cells' loads in flight.
- **Register reduction / launch bounds.** Occupancy is secondary, and the tried
  variant spilled. Not repeated.
- **Vectorized V loads.** Each row load is already coalesced (64 B per warp
  instruction); latency, not transaction count, is the issue.
- **Exact FFMA chain restructuring, split-K, MMA, fast-math.** The chain is not
  critical. The others change arithmetic and are unnecessary for the measured
  bottleneck.
- **K-load coalescing** (ncu estimates 4.6% from 33% excess sectors in the score
  phase). Real but small; later.
