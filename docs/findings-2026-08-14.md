# Findings — 2026-08-14 stabilization pass

This report closes Tasks 1–16 of the stabilization plan. It records the
project's actual purpose, the defects found, the final end-to-end result, and
the boundary between what is demonstrated and what remains research.

## 1. Executive verdict

ARGUS is a heterogeneous KV-cache **storage runtime**. Its job is to keep
recent pages at high fidelity and move older pages into progressively cheaper
GPU or CPU representations. It is not a low-bit attention engine and it is not
a general inference accelerator.

After removing three hidden FP16 copies and a benchmark-lifetime leak, ARGUS
does reduce peak VRAM at long contexts. The saving reaches **131.95 MiB
(7.7%) at 16K** on the measured 0.5B model. The trade-off is currently too
large for latency-sensitive serving: **TPOT is 4.2x baseline at 16K**.

The honest product status is therefore:

- **Demonstrated:** configurable tiering, native codecs, real long-context
  VRAM reduction, plugin replacement, HuggingFace cache ownership, live
  external Ollama validation.
- **Research prototype:** low-latency decode over compressed pages.
- **Not demonstrated:** a context where baseline OOMs and ARGUS survives;
  downstream quality of the lossy archival tiers; real vLLM cache ownership.

## 2. Final downstream measurement

Artifact: `docs/measurements/downstream-2026-08-14.json`.

Environment: Qwen2.5-0.5B-Instruct, RTX 3050 Ti Laptop 4 GB, torch
2.12.0+cu130, FP16, batch 1, page size 1024, 64 generated tokens, three
measured repeats after one warm-up. Each arm explicitly releases its native
callbacks before the next arm starts.

| context | baseline TTFT | ARGUS TTFT | baseline TPOT | ARGUS TPOT | baseline VRAM | ARGUS VRAM | VRAM change |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 512 | 0.044 s | 0.148 s | 18.62 ms | 28.69 ms | 982.2 MiB | 988.2 MiB | +0.6% |
| 1,024 | 0.076 s | 0.181 s | 18.55 ms | 30.21 ms | 1007.1 MiB | 1007.1 MiB | 0.0% |
| 2,048 | 0.152 s | 0.273 s | 19.24 ms | 30.85 ms | 1056.8 MiB | 1056.9 MiB | 0.0% |
| 4,096 | 0.316 s | 0.385 s | 19.14 ms | 40.21 ms | 1149.4 MiB | 1137.4 MiB | -1.0% |
| 8,192 | 0.718 s | 0.880 s | 17.85 ms | 52.51 ms | 1340.4 MiB | 1280.5 MiB | **-4.5%** |
| 16,384 | 1.819 s | 3.992 s | 18.84 ms | 79.78 ms | 1722.5 MiB | 1590.6 MiB | **-7.7%** |

### Interpretation

The memory crossover begins around 4K on this configuration. Below that,
runtime overhead is equal to or larger than the storage saved. Above it, the
absolute and percentage saving grow with context.

TTFT improved materially after JL operators were made lazy: at 8K it is only
1.23x baseline. At 16K another archival boundary is crossed and TTFT rises to
2.19x. Decode is the more important problem. TPOT grows from 1.54x baseline at
512 to 4.23x at 16K.

This shape follows the implementation. HuggingFace expects a contiguous FP16
K/V tensor, so ARGUS currently decompresses stored pages and assembles that
tensor again on every token. Compression saves persistent storage, while
reconstruction and concatenation add work proportional to cache size.

Page-size experiments reduced constants but did not change that complexity:

- page 512 at 16K: 1626.7 MiB, 122.08 ms TPOT;
- page 1024 at 16K: 1590.6 MiB, 79.78 ms TPOT.

Page 1024 was selected as the best measured compromise. It is not a universal
preset and cannot solve the architectural materialization cost.

### What this does not prove

Both arms fit at 16K. Consequently, the stronger claim “ARGUS prevents an OOM
that baseline would hit” remains unsupported. That requires a larger model or
longer-context run where baseline actually fails and ARGUS completes under the
same conditions. The result here proves **VRAM reduction**, not **OOM
survival**.

## 3. Perplexity result and its narrow scope

| arm | perplexity | delta |
|---|---:|---:|
| baseline | 33.9169 | — |
| ARGUS | 33.8993 | -0.0176 |

Scoring was token-by-token through the tested cache; a batched pass would have
bypassed the behavior under test. Recorded tier occupancy was
`{active: 24, fp8: 24}`.

Only FP8 was reached. The result is consistent with near-lossless storage but
does not characterize INT4, INT2, 1-bit, or JL. No downstream quality claim is
made for those tiers.

## 4. Performance and correctness defects fixed

| defect | consequence | resolution |
|---|---|---|
| Full decompressed K/V cached per layer | Persistent FP16 mirror cancelled the compression saving | Fill one output tensor directly from pages; keep no decompressed mirror |
| Prefill staging grew to the entire prompt | A second full FP16 copy survived after native ingestion | Stream complete pages to C++; retain only the final partial page |
| Python tier pools allocated beside native storage | Large unused per-layer buffers | Allocate legacy pools only if the legacy path is explicitly used |
| Native manager retained Python callbacks | C++→Python→C++ cycle contaminated later benchmark arms | Callbacks use weak references; `close/reset` also releases them immediately |
| JL operators initialized for every layer | Paid projection setup even when no page reached JL | Construct operators only when archival demand reaches the tier |
| Prefill produced logits for every position | 8K created a 2.32 GiB logits tensor and caused a false OOM | Use `logits_to_keep=1`; discard every pre-fix result |
| Unbounded tier sent `-1` to `torch.zeros` | Archival pipelines failed immediately | Allocate unbounded storage per page |
| Source distribution omitted headers | Tarball installation could not compile | Include native headers in `MANIFEST.in` |
| Divergent attention wrapper copy | Root import silently missed new options | Replace with a re-export shim and enforce identity in tests |
| Projection prefetch cached undefined tensors | Later attention saw an empty page | Skip unsafe background speculation |

The first benchmark reported ARGUS using 1564.3 MiB versus baseline 1340.4
MiB at 8K. After the storage fixes, the final result is 1280.5 MiB. The sign
changed because the earlier number measured redundant implementation buffers,
not the intended tiered-cache design.

## 5. JL tier: useful, but for a corrected reason

Artifact: `docs/measurements/jl-2026-08-14.json`.

| result | value |
|---|---:|
| JL median relative L2 | 0.413 |
| shipped INT2 at equal 4x storage budget | 0.565 |
| layers where JL wins | 20 / 24 |

The old “low-rank structure” explanation was wrong. The reconstruction
operator uses a token-axis smoothness prior. Rank-4 random signals recover no
better than white noise (1.106 versus 1.111 relative error), while real-page
error correlates with roughness at r = 0.988. A test now fixes this distinction.

This is a reconstruction result on one model and keys only. It is not a
perplexity or retrieval result.

## 6. Runtime adapters

### Ollama

Five tests passed against a live Ollama 0.32.11 server and
`qwen2.5:0.5b`. The adapter needed no protocol changes. It remains correctly
labelled external: it configures and measures Ollama but cannot own the KV
cache inside the separate server process.

### vLLM

The installed vLLM 0.27.1 API was probed in an isolated torch 2.13 environment.
The old model-class `LlamaAttention.forward` wrapper merely attached an
attribute that vLLM never consumed; it did not manage or compress vLLM blocks.

The adapter now fails closed with `manages_kv_cache=False` and an empty
supported-version range. A real implementation belongs at vLLM's
`KVConnectorBase_V1` and/or registered custom `AttentionBackend` boundary.
Ten adapter tests pass against the installed package. The package lacks its
compiled `vllm._C` in this environment, so a live engine generation was not
possible. Full probe details are in `docs/vllm-verification.md`.

## 7. What the project can become

ARGUS has a defensible core as a **memory-capacity layer for long-context
serving**. The valuable asset is the configurable policy/data-plane split:
tier plugins decide storage cost and fidelity, while the native manager owns
page lifecycle and spill.

The next milestone must combine this store with an attention kernel that reads
compressed pages directly. In practical order:

1. implement an attention backend over ARGUS pages, avoiding full-cache FP16
   materialization;
2. integrate that backend through an official serving-runtime seam;
3. benchmark TPOT, throughput, and concurrent requests while preserving the
   measured VRAM curve;
4. exercise every lossy tier in perplexity and retrieval tests;
5. run a controlled baseline-OOM/ARGUS-survival experiment.

Until steps 1–3 succeed, ARGUS is suitable for research and batch-style
capacity experiments, not latency-sensitive production serving.

A Turkish implementation note covering low-context bypass, pressure-aware
activation, simpler tier pipelines, fixed workspaces, direct paged attention,
and balanced success gates is recorded in
`docs/optimization-notes-2026-08-14-tr.md`.
